## Architecture Decisions

- Auth is Clerk, protected by default at the proxy level (`proxy.ts`, allow-list of public routes) rather than per-page checks — matches 03-auth.md's "protect everything else by default" requirement and keeps future routes secure without remembering to add checks.
- Authorization for Project/ProjectCollaborator data is enforced at the application layer (every Prisma query filtered by the Clerk `userId` from `auth()`), not Postgres RLS — there's a single trusted `DATABASE_URL` connection, not per-user DB roles. Applied in `06-project-apis.md`'s routes: list is scoped by `where: { ownerId: userId }`; rename/delete fetch-then-compare `project.ownerId !== userId` before mutating, returning `403` on mismatch and `404` if the project doesn't exist.
- Rate limiting deferred for the Project CRUD routes (06-project-apis.md) — internal, Clerk-authenticated editor feature, no public/anonymous surface or per-call paid resource. Revisit if these routes become public or see abuse.
- Mutations from the editor UI (07-wire-editor-home.md) don't hold client-side project-list state — the editor home page is a server component that fetches owned/shared projects on each render, and the `useProjectActions` hook triggers a `router.refresh()` (rename/non-active delete) or `router.push` (create success, delete of the active workspace) to get fresh server data rather than reconciling an optimistic local list. Simpler and matches the spec's "no client-side fetching for initial load" intent extended to post-mutation state.
- `types/project.ts`'s `Project` dropped its `slug` field (leftover from 04's mock-only implementation) — the real `Project` Prisma model has no slug column. The "room ID preview" shown in the create dialog is a client-only `slugify(name) + "-" + shortRandomSuffix` computed in `useProjectActions`, purely cosmetic; the actual workspace URL uses the real DB-assigned `project.id` returned by `POST /api/projects`, per the spec's "project ID and Liveblocks room ID should stay aligned."
- Project access checks (08-editor-workspace-shell.md) collapse "project doesn't exist" and "project exists but you can't see it" into the same `null`/`AccessDenied` outcome in `lib/project-access.ts`, rather than a distinct 404 — matches the spec's own wording ("non-existent projects also show `AccessDenied`") and avoids leaking project-ID existence to unauthorized users as a side effect.
- `components/editor/workspace-shell.tsx` includes a left sidebar-toggle button in `workspace-navbar.tsx` even though the spec's "Layout" section only lists "share button and AI sidebar toggle" as navbar actions — without it, the reused `ProjectSidebar` (an overlay that starts closed) would have no way to open. Treated as implied by "existing `ProjectSidebar` on the left" rather than as scope creep. Same reasoning led to wiring the sidebar's create/rename/delete straight to `useProjectActions`, since `ProjectSidebar`'s action props aren't optional — this also closes the loop 07 left open (`useProjectActions`' `currentProjectId` param, previously always `undefined`, now receives the real room id here).
- The workspace placeholders' visual design (dot-grid canvas, icon badges, card-based AI panel, navbar title/subtitle) deliberately reuses only existing `ui-context.md` tokens/radii/type scale — no new hex values, fonts, or components outside that system, even though the user's reference screenshot was the trigger. Treated as a composition/copy exercise within the established design system, not a rebrand.
- Client-only rendering (needed for `UserButton` to dodge Clerk's SSR hydration quirk, and for any future case) should use `hooks/use-is-mounted.ts`'s `useSyncExternalStore`-based `useIsMounted()`, not a `useState` + `useEffect(() => setState(true), [])` pattern — this repo's ESLint config enables `react-hooks/set-state-in-effect`, which errors on the latter.
- `ProjectSidebar` now has two visual variants (`"overlay"` default, `"docked"` opt-in via prop) rather than being redesigned in place — the floating-overlay presentation is an established, working pattern from 02-editor-chrome.md used on the `/editor` home page, and the user's reference screenshot only concerned the `/editor/[roomId]` workspace layout. Splitting by variant avoids regressing the home page while still matching the reference exactly where it was asked for. If a future request wants the docked/flush treatment on the home page too, extend by passing `variant="docked"` there rather than changing the default.
- Share dialog API routes (09-share-dialog.md) deliberately do **not** reuse `lib/project-access.ts`'s `getAccessibleProject` for their owner/collaborator checks, even though the logic overlaps — that helper's "collapse not-found and no-access into one `null`" behavior is a page-level anti-enumeration choice (08's `AccessDenied` UI), while these JSON API routes follow the earlier-established 06-project-apis.md precedent of distinct `404`/`403` responses. The small duplication (an inline `ownerId` check per route) was judged better than forcing one helper to serve two different security-response philosophies.
- Collaborator removal (`DELETE /api/projects/[projectId]/collaborators`) takes the email in the JSON body, not as a URL path segment — avoids `@`/`+`/case-encoding edge cases that come with putting an email address directly in a URL, at the cost of being a slightly less "RESTful" resource path. Consistent going forward: any future per-collaborator route should default to body-based identification unless there's a strong reason not to.
- The recurring `ETIMEDOUT` DB errors are treated as an infrastructure/network symptom to make resilient against, not a bug to root-cause further from this side — both `pooled.db.prisma.io` and Clerk's `*.clerk.accounts.dev` have independently timed out multiple times across this session while checking out fine when tested directly from this environment, pointing at the user's local network rather than the app. `lib/prisma.ts`'s bounded `connectionTimeoutMillis` and the new `DataUnavailable` fallback (see Completed) are the actual fix — bound the damage, don't chase a network problem outside the app's control.
